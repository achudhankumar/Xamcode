01 — HOW TO USE THIS GUIDE
Treat this as a Website Standard Operating Procedure (SOP). For every project, copy the checklists into a tracker and mark
each item: Not Started / In Progress / Passed / Not Applicable / Blocked.
The core order is: business purpose → requirements → information architecture → design system → component
contracts → implementation → data/security → testing → legal/compliance → deployment → maintenance.
Do not use “the page looks good” as a definition of done. A production feature is done only when its expected behavior, error
handling, security, accessibility and tests are documented.

■ Every page has an owner and purpose.

■ Every interactive element has defined states and expected outcomes.

■ All user-data flows are documented.

■ Third-party assets/dependencies have a license or permission record.

■ Security, accessibility, performance and SEO checks have been run.

■ Required legal pages/disclosures are accurate and published.

■ Backups, monitoring and rollback are tested.

■ Known defects are documented and explicitly accepted.

03 — REQUIREMENTS & SCOPE
Write one source-of-truth requirements document before coding. This is your defense against scope confusion and accidental
behavior.
User story: As a [user], I want [action], so that [outcome]. Acceptance criteria must be measurable.
Example: a contact form should validate input, submit safely, prevent duplicates, show success/error states, send the configured
notification, log only necessary operational data and remain usable by keyboard/screen reader.

■ Problem statement and success metric defined.

■ Target users/personas and accessibility needs defined.

■ Page list and navigation map approved.

■ Feature list prioritized: P0 launch-blocking / P1 important / P2 later.

■ Roles and permissions defined.

■ Data fields, purpose, retention and deletion expectations documented.

■ Third-party integrations and fallback behavior documented.

■ Non-functional requirements: speed, uptime, browser/device support, security, accessibility.

■ Legal/compliance owner assigned.

■ Out-of-scope items documented.
Change-control rule
After approval, new production behavior becomes a change request. Record impact on UI, API, database, tests, security,
privacy, legal text, schedule and rollback.

07 — ENGINEERING STANDARDS
Choose technology based on requirements, team capability, security, maintenance and deployment—not trend alone.

■ Use version control (Git) with meaningful commits.

■ Keep development, staging and production environments separated.

■ Never commit passwords, API keys, private tokens or production secrets.

■ Use environment variables/secret management.

■ Pin and regularly update dependencies; remove unused packages.

■ Use linting, formatting and type checking where the stack supports them.

■ Use reusable components and avoid copy-paste business logic.

■ Keep configuration separate from application logic.

■ Handle errors centrally; do not expose stack traces or secrets to users.

■ Validate input on the server even when the client validates it.

■ Use migrations for database schema changes.

■ Document architecture and major technical decisions.
Recommended repository structure
A typical app should separate UI/components, routes/pages, services/API, data models, validation, authentication/authorization,
configuration, tests, public assets and documentation. Exact folders depend on the framework.

08 — DATA, API, DATABASE & AUTHENTICATION
Assume every client-side input can be modified by an attacker. The server is the final authority.

■ Define data ownership and purpose for every field.

■ Collect the minimum data needed for the feature.

■ Validate type, length, format, range and business rules server-side.

■ Use parameterized queries/ORM safely; never concatenate untrusted SQL.

■ Use authorization checks on every protected resource, not just hidden buttons.

■ Separate authentication from authorization.

■ Use secure password hashing; never store plaintext passwords.

■ Use secure session/token handling and appropriate expiration/revocation.

■ Protect password reset, email verification and account recovery flows.

■ Rate-limit authentication and high-risk endpoints.

■ Log security-relevant events without logging passwords, tokens or unnecessary personal data.

■ Back up databases and test restoration.

■ Define deletion/anonymization procedures where required.

09 — ACCESSIBILITY
Use WCAG 2.2 as the practical international accessibility baseline. W3C organizes it around perceivable, operable,
understandable and robust principles. Choose and document a target level—commonly AA for serious public-facing products.
WCAG is a technical standard; legal obligations depend on jurisdiction and service.

■ All meaningful images have useful alt text; decorative images are marked decorative.

■ Every interactive element is keyboard reachable and has a visible focus indicator.

■ Focus order is logical.

■ Forms have real labels, instructions and accessible error messages.

■ Color is not the only signal for state.

■ Text can be resized/zoomed without breaking essential functionality.

■ Headings follow a logical hierarchy.

■ Buttons are buttons; links are links.

■ Dialogs manage focus correctly.

■ Animations can be reduced/disabled where appropriate.

■ Media has appropriate captions/transcripts when needed.

■ Test with keyboard-only navigation and at least one screen reader workflow.
Reference: WCAG 2.2 is a W3C Recommendation; the latest W3C guidance describes A/AA/AAA conformance levels and four principles.

12 — PRIVACY & INDIA LEGAL BASELINE
India's Digital Personal Data Protection Act, 2023 (DPDP Act) regulates processing of digital personal data in the circumstances
specified by the Act. MeitY published the Digital Personal Data Protection Rules, 2025; commencement/enforcement is staged
by government notification, so implementation dates and obligations must be checked against the current official position before
launch.
Do not copy a generic privacy policy and assume compliance. Map your actual collection, purposes, notices, consent/other
lawful basis, processor/vendor relationships, security, retention and user-rights workflows to the law and your actual operations.

■ Inventory every personal-data collection point: signup, contact, newsletter, analytics, payments, support, uploads.

■ Document why each data element is collected and whether it is necessary.

■ Provide clear privacy information at or before collection as required.

■ Implement consent/notice flows where required; do not use preselected or deceptive choices.

■ Provide user-facing mechanisms required by applicable law for access/correction/deletion/withdrawal or other rights.

■ Define retention and deletion schedules.

■ Document third-party processors/vendors and data flows.

■ Secure personal data in transit and at rest as appropriate.

■ Have a data-breach/incident process and legal escalation path.

■ Review whether children/minors, sensitive use cases or cross-border processing trigger extra requirements.

■ Keep policy versions and records of important consent/notice events where appropriate.
Other India legal modules to assess

■ Information Technology Act, 2000 and applicable rules/directions.

■ Consumer Protection Act, 2019 and Consumer Protection (E-Commerce) Rules, 2020 if e-commerce applies.

■ Consumer Protection guidelines concerning misleading advertisements/endorsements and dark patterns where applicable.

■ CERT-In directions and incident-reporting requirements where applicable.

■ Legal Metrology requirements for packaged goods/e-commerce where applicable.

■ Tax/GST, company/LLP/sole-proprietor, accounting and sector-specific requirements where applicable.

■ Advertising, IP, trademark, competition, employment and contract law as relevant.

16 — DEBUGGING & INCIDENT WORKFLOW
Do not patch symptoms blindly. Debugging should produce a reproducible case and a verified root cause.
Bug workflow

■ 1. Reproduce the bug.

■ 2. Record environment: browser/device/version, user role, URL, timestamp.

■ 3. Capture exact steps and expected vs actual result.

■ 4. Check console/network/server/database logs as appropriate.

■ 5. Identify root cause and blast radius.

■ 6. Apply the smallest safe fix.

■ 7. Add/adjust a regression test.

■ 8. Re-test the original case plus adjacent flows.

■ 9. Review security/privacy impact.

■ 10. Deploy through the normal release process.

■ 11. Record what changed and whether monitoring confirms recovery.
Severity model

Example
Action

P1/High

Schedule fix
P3/Low
Cosmetic/minor inconvenience
Backlog if acceptable

17 — PERFORMANCE & RELIABILITY
Performance is a feature. Define budgets before launch rather than chasing an arbitrary score later.

■ Optimize images and use responsive formats.

■ Lazy-load non-critical media where appropriate.

■ Minimize JavaScript and third-party scripts.

■ Cache static assets safely.

■ Use CDN where appropriate.

■ Measure real-user performance where possible.

■ Define target response times for important APIs.

■ Use timeouts and safe retries for external services.

■ Prevent retry storms and duplicate transactions.

■ Monitor uptime, error rate, latency and key business events.

■ Have backups and a tested restore procedure.

■ Define recovery objectives appropriate to business risk.
Suggested performance budget (starting point)
Set your own target based on product needs. A useful starting discipline is: keep critical pages lightweight, avoid unnecessary
third-party scripts, measure on mid-range mobile hardware and slower networks, and investigate regressions rather than
accepting them as “normal.”

18 — DEPLOYMENT & PRODUCTION LAUNCH
Production deployment is a controlled release, not simply “upload the folder”.

■ Domain ownership and DNS access are documented.

■ HTTPS certificate is active and renewal is monitored.

■ Production environment variables/secrets are configured securely.

■ Database migrations are reviewed and backed up.

■ Build is reproducible from version control.

■ Staging environment matches production closely enough for meaningful testing.

■ Error monitoring and uptime monitoring are active.

■ Analytics/privacy configuration is verified.

■ Robots/indexing settings are correct for launch.

■ Sitemap/canonical/metadata are correct.

■ Legal pages are published and linked.

■ Support/contact route works.

■ Backup exists and restoration has been tested.

■ Rollback plan is known and tested.

■ Launch owner is named.
Release sequence
Build → automated checks → staging → smoke test → backup → migration (if any) → production deploy → smoke test →
monitor → sign-off. Do not make unrelated code changes during the launch window.

19 — MAINTENANCE & CHANGE MANAGEMENT
A website is never truly “finished”; it enters maintenance.

■ Weekly: review errors, uptime, broken forms, critical user journeys.

■ Monthly: dependency/security updates, backups/restore spot-check, analytics anomalies, broken links.

■ Quarterly: access review, privacy/vendor review, license review, accessibility spot-check, disaster-recovery exercise where
appropriate.

■ After major change: regression test affected workflows and update documentation.

■ Keep dependencies and runtime versions supported.

■ Remove unused accounts, API keys, integrations and packages.

■ Review legal policies when business practices or laws change.

■ Archive old content/assets according to retention policy.
Versioning rule
Every release should have a version/date, change summary, affected components, migration notes, test evidence, rollback
method and owner.

IMPORTANT LEGAL NOTE
The presence of a law/rule in this guide does not mean it automatically applies to every website. Applicability can depend on the
entity, data, users, geography, business model, sector, thresholds, contractual arrangements and the
commencement/enforcement status of a provision. For a revenue-generating or high-risk website, have counsel review the
actual business model and final policies.
FINAL RULE
Build → test → document → review → launch → monitor → update. If you skip one of these, you are increasing avoidable
risk. The goal is not perfection; it is controlled, explainable, testable and maintainable engineering.
